# Recipe provenance

Måltiden ships a shared catalogue of seed recipes (rows in `recipes` with
`household_id IS NULL`). Every household sees them, and menu generation picks
from them. This doc records where they came from and how the third-party ones
get replaced.

## Inventory

| `recipes.source` | Count | Defined in | Origin |
|---|---|---|---|
| `ica.se` | 110 | `backend/migrations/012_seed_100_recipes.sql` | Generated by `tools/scrape_ica_recipes.py` from ICA.se category pages. Names, ingredient lists and step text are copied from ICA, only lightly cleaned up (migrations 012 and 014). |
| `maltiden-seed` | 20 | `backend/migrations/004_seed_recipes.sql` (5), `008_seed_more_recipes.sql` (15) | Short, generic Swedish classics written for the project. Nothing suggests they were scraped, but the repo doesn't record who wrote them either. |
| `NULL` | — | created at runtime | Household-owned recipes (`household_id` set), entered by users by hand or through the recipe parser. This is user content, not seed data. |

Migration `021_add_recipe_source.sql` adds the `source` column and labels the
130 seed rows by explicit id. `recipe_source_migration_test.go` pins these
counts, so the test fails if the seed set changes without this doc changing too.

Find them in a live database:

```sql
SELECT source, COUNT(*) FROM recipes WHERE household_id IS NULL GROUP BY source;
SELECT id, name FROM recipes WHERE source = 'ica.se' ORDER BY name;
```

## Why the ICA recipes are a risk

A plain list of ingredients is generally treated as facts, but the step-by-step
wording in the ICA recipes is ICA's own text, copied word for word. ICA's site
terms also probably restrict automated collection. Together that means
copyright, and possibly the EU database right, on content we republish to every
user. This is a risk assessment, not legal advice. Treat the rows as content
to replace before promoting the app widely.

## Replacement plan

1. **Stop adding to it.** Do not re-run `tools/scrape_ica_recipes.py`. Keep it
   in the repo only as a record of how migration 012 was produced. Delete it
   once step 4 has shipped.
2. **Write replacements.** For each `ica.se` row, write an original recipe for
   the same kind of dish: our own name, amounts checked in a real kitchen, and
   steps written from scratch (not a paraphrase of the ICA text). Also fine:
   recipes from an openly licensed source, with attribution kept in `source`
   (e.g. `source = 'cc-by:<origin>'`). Keep tags and emoji so menu variety
   (vegetarian quota, protein/cuisine spread) stays the same.
3. **Ship them additively.** A new migration inserts the replacements with new
   ids and `source = 'maltiden-original'` (or the licence tag). It stays in
   the seed-lint glob (`*_seed*.sql`) so CI's content checks cover it.
4. **Retire the ICA rows.** A follow-up migration, in one transaction:
   - repoints `menu_days.recipe_id` from each ICA id to its replacement, using
     an explicit old→new mapping in the migration (or sets it to `NULL` when
     there is no counterpart);
   - deletes the `source = 'ica.se'` rows.
   `menu_days.recipe_id` has a foreign key to `recipes(id)`, so the repoint
   has to run before the delete. Take a backup first
   (see [deploy.md](deploy.md#backups)).
5. **Optional stop-gap.** If replacement takes a while, the recipe queries in
   `internal/storage/sqlite/recipe_storage.go` can exclude
   `source = 'ica.se'` from the shared catalogue with one extra `WHERE`
   clause. The catalogue drops to 20 seed recipes, which hurts menu variety,
   so this is a product call for the maintainers, not a default.

## Rules for new seed content

- Every new seed row sets `source`.
- Never commit scraped third-party text. If a recipe is adapted from somewhere,
  record where in `source` and make sure the licence allows it.
