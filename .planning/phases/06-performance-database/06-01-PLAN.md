Purpose: Tjek API calls are the slowest path in the app — fetching catalogs sequentially with 30s timeout and no caching means every offer search makes multiple slow HTTP calls. Caching alone provides ~600x speedup on repeat requests; concurrent fetching provides ~5x on first request.
Output: Refactored tjek_service.go with caching layer, concurrent fetching, retry logic, and reduced timeouts.
</objective>

<task type="auto">
  <name>Task 1: Add in-memory TTL cache for Tjek API responses</name>
  <files>backend/internal/services/tjek_service.go</files>
  <action>
Add a simple thread-safe TTL cache to TjekService. Implementation:

1. Define a `cacheEntry` struct with `data interface{}`, `expiresAt time.Time` fields.
2. Add a `cache` field to `TjekService` — `map[string]cacheEntry` protected by `sync.Mutex`.
3. Add `getFromCache(key string) (interface{}, bool)` and `setCache(key string, data interface{}, ttl time.Duration)` methods.
4. Cache keys: `"catalogs:{lat}:{lng}:{radius}"`, `"stores:{lat}:{lng}:{radius}"`, `"hotspots:{catalogID}"`.
5. TTL: 1 hour for catalogs and stores, 1 hour for hotspots (offers change weekly, 1h is safe).
6. Wrap `getCatalogs`, `getStores`, and `getCatalogOffers` to check cache before HTTP call.
7. Initialize cache map in `NewTjekService()`.

Do NOT use sync.Map (it's optimized for read-heavy with stable keys, not TTL expiry). Use sync.Mutex + plain map — simpler, correct, and fast enough for this use case.

Also reduce the HTTP client timeout from 30s to 10s (PERF-08) in `NewTjekService()`.
  </action>
  <verify>go build ./... compiles without errors. Verify cache fields and methods exist in tjek_service.go.</verify>
  <done>TjekService has in-memory TTL cache. getCatalogs/getStores/getCatalogOffers check cache before HTTP. HTTP timeout reduced to 10s. Cache entries expire after 1 hour.</done>

<task type="auto">
  <name>Task 2: Add concurrent catalog fetching and retry with backoff</name>
  <files>backend/internal/services/tjek_service.go</files>
  <action>
Two changes:

**Concurrent catalog offer fetching:**
In `SearchOffers` and `GetTopDiscounts`, the loop `for _, catalog := range catalogs` currently calls `getCatalogOffers` sequentially. Refactor to:
1. Use `sync.WaitGroup` + buffered channel to fetch catalog offers concurrently.
2. Limit concurrency to 5 goroutines using a semaphore channel (`sem := make(chan struct{}, 5)`).
3. Collect results via a buffered results channel or a mutex-protected slice.
4. Apply the same filtering logic (isGroceryStore, excludeMap) BEFORE spawning goroutines to avoid unnecessary HTTP calls.

**Retry with exponential backoff:**
Create a `doWithRetry(fn func() (*http.Response, error)) (*http.Response, error)` helper method on TjekService:
1. Max 3 attempts.
2. Backoff: 0ms (immediate), 100ms, 200ms.
3. Retry on: network errors, 5xx responses, 429 (rate limit).
4. Do NOT retry on: 4xx (except 429), context cancellation.
5. Use this helper in `getCatalogs`, `getStores`, and the HTTP call within `getCatalogOffers`.

Also replace the two bubble sorts in `GetAvailableStores` and `GetTopDiscounts` with `sort.Slice` (PERF-10 fix, trivial while here).
  </action>
  <verify>go build ./... compiles. Verify sort.Slice usage replaced bubble sort. Verify WaitGroup/semaphore pattern in SearchOffers and GetTopDiscounts.</verify>
  <done>Catalog offers fetched concurrently (max 5). Retry with exponential backoff on transient failures. Bubble sorts replaced with sort.Slice.</done>
