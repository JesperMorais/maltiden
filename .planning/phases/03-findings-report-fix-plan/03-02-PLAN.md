  <files>.planning/FIX-PLAN.md</files>
  <action>
Read FINDINGS-REPORT.md (created in 03-01). Create `.planning/FIX-PLAN.md` with the following structure:

1. **Overview** — Total effort estimate, number of batches, recommended ordering rationale

2. **Batch organization** — Group findings into sprint-sized batches (each batch = a focused work session of 4-8 hours). Organize by:
   - **Dependency order:** Infrastructure fixes before feature fixes (e.g., FK enforcement before transaction safety, storage interfaces before testing improvements)
   - **Area cohesion:** Related fixes grouped together to minimize context-switching (all auth fixes in one batch, all DB config in one batch, etc.)
   - **Severity gradient:** Earlier batches are mostly critical/high, later batches are medium/low
   - **Risk reduction:** Each batch independently improves backend health — no batch depends on a later batch

3. **Batch structure** — For each batch:
   - **Batch name** (e.g., "Batch 1: Critical Security Fixes")
   - **Priority tier** (Immediate / High / Medium / Low)
   - **Estimated effort** (hours)
   - **Findings addressed** (list of unified IDs from FINDINGS-REPORT.md with one-line descriptions)
   - **Dependencies** (which batches must complete first, if any)
   - **Key files touched** (so developer knows what code areas to focus on)
   - **Definition of done** (what's true when this batch is complete)

4. **Batch ordering rationale:**
   - Batch 1: Critical security + auth (JWT secret, shopping auth, IDOR) — blocks everything else, highest risk
   - Batch 2: Data integrity (FK enforcement, transactions, WAL mode) — foundation for reliable operations
   - Batch 3: Error handling infrastructure (sentinel errors, response helper, error logging) — improves all subsequent development
   - Batch 4: Input validation (request limits, field validation) — systematic sweep using error infrastructure from batch 3
   - Batch 5: Performance — external API (Tjek caching, concurrent fetching, retry) — biggest user-facing improvement
   - Batch 6: Performance — database (N+1 fix, connection pool, indexes, query timeouts)
   - Batch 7: Architecture improvements (storage interfaces, domain separation, DI) — enables future development
   - Batch 8: Deployment & observability (fly.toml, health check, structured logging, rate limiting, CORS)
   - Batch 9: Code quality & polish (remaining medium/low items)

   Adjust batch count and grouping based on actual finding counts — aim for 6-10 batches total. Merge small batches, split large ones. Each batch should be completable in one focused session.

5. **Implementation notes** per batch — any gotchas, ordering within the batch, or things to watch out for.
