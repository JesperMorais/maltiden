  <action>
Review the backend for performance issues across these dimensions. Read relevant source files, SQL migrations, and deployment config:

**1. Database Query Patterns**
- Trace all SQL queries: are there N+1 patterns beyond the known shopping list one?
- Check for missing WHERE clause indexes (review queries against migration schemas)
- Are there full table scans that should use indexes?
- Are queries selecting more columns than needed (SELECT *)?
- Are there opportunities for batch operations instead of loops?

**2. External API Integration (Tjek Service)**
- Map all external HTTP calls: how many per user request?
- Sequential vs parallel opportunities
- Response sizes and parsing efficiency
- Timeout configuration and failure modes
- Caching strategy (or lack thereof) — what's the cost of no cache?

**3. Algorithm Efficiency**
- Review menu generation algorithm: what's the time complexity?
- Review shopping list aggregation: are there unnecessary iterations?
- Review the bubble sort instances: impact and fix complexity
- Any string operations that could be optimized (e.g., repeated concatenation)?

**4. Database Configuration**
- SQLite PRAGMAs: what's set vs what should be set (WAL, foreign_keys, journal_size_limit, synchronous, cache_size)?
- Connection pooling: is sql.DB configured with max open/idle connections?
- Is the database opened once and reused, or reopened?

**5. Memory & Resource Usage**
- Request body size limits (already known from Phase 1, but assess pattern)
- Are there unbounded in-memory collections (slices that grow without limit)?
- Image/file handling (if any)?
- Goroutine leaks or unbounded concurrency?

**6. Deployment & Infrastructure**
- Dockerfile: multi-stage build efficiency, image size, layer caching
- fly.toml: memory allocation, scaling config, health checks
- Cold start optimization: what runs at startup, can anything be lazy?
- Are there missing health check or readiness probe concerns?

Write findings to 02-02-FINDINGS.md using the same severity format as Phase 1. Each finding should include:
- Severity and category
- What the performance issue is
- Quantified impact where possible (e.g., "20 sequential HTTP calls vs 5 concurrent batches")
- Which files are affected
- Concrete recommendation for Phase 3 fix plan

Use severity ratings:
- Critical: Issues that cause outages or data loss under normal load
- High: Issues that cause noticeable degradation or will block scaling
- Medium: Suboptimal patterns that waste resources but don't cause visible problems yet
- Low: Micro-optimizations, polish

Reference known issues from Phase 1/CONCERNS.md where they fit into systemic patterns, but don't just re-list them. Add new context: quantify impact, identify related patterns, propose solutions.
