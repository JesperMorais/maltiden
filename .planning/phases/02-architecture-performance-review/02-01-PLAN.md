  <action>
Review the backend architecture systematically across these dimensions. For each, read the relevant source files and identify systemic issues (not individual bugs — Phase 1 covered those):

**1. Layer Responsibility & Separation**
- Do handlers ever contain business logic that belongs in services?
- Do services ever access HTTP concepts (request, response, headers)?
- Do storage layers ever contain business rules?
- Is the domain package truly dependency-free?
- Are there circular or upward dependencies between layers?

**2. Dependency Patterns**
- Services depend on concrete storage types (no interfaces) — assess impact on testability and future DB migration
- How is dependency injection wired? Is it consistent?
- Are there hidden dependencies (package-level vars like JWT secret)?
- Could any service be tested in isolation today?

**3. Error Propagation**
- Trace error flow from storage → service → handler → HTTP response
- Identify where errors are lost, transformed incorrectly, or leak internals
- Assess the string-matching error pattern: how many places does it appear? What's the blast radius of changing an error message?
- Map which errors produce which HTTP status codes — is it consistent?

**4. Code Organization**
- Package structure: is internal/ used correctly? Is pkg/ appropriate for what it contains?
- Are there domain concepts split across packages that should be co-located?
- Is the router file doing too much (wiring + route definitions)?
- Are there missing abstractions (e.g., no error type, no response helper, no validation framework)?

**5. Configuration & Startup**
- How is configuration loaded? Is it validated?
- What happens if required env vars are missing?
- Is the startup sequence correct (migrations before serving)?
- Are there race conditions in initialization?

**6. Cross-cutting Concerns**
- Logging: what's logged vs swallowed?
- Observability: could you debug a production issue with current tooling?
- Middleware: is it applied consistently? Any gaps?

Write findings to 02-01-FINDINGS.md using the same severity format as Phase 1 (critical/high/medium/low). Each finding should include:
- Severity and category
- What the systemic issue is
- Which files/patterns are affected
- Why it matters (impact on development velocity, reliability, security)
- Concrete recommendation for Phase 3 fix plan

Use severity ratings consistently with Phase 1:
- Critical: Systemic issues that cause data loss, security bypass, or production failures
- High: Patterns that will cause bugs as codebase grows, or block important capabilities
- Medium: Consistency issues, missing abstractions, maintainability debt
- Low: Polish, idiomatic improvements, nice-to-haves

Do NOT re-list individual issues from Phase 1. Instead, identify the systemic PATTERNS those issues reveal (e.g., "error handling is fragile across all handlers because there are no sentinel errors" rather than listing each handler's error handling bug).
