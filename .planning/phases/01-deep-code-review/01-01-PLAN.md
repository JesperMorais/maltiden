  <name>Task 1: Review auth middleware, JWT handling, CORS, and password utilities</name>
  <files>backend/pkg/middleware/auth.go, backend/pkg/middleware/cors.go, backend/pkg/utils/jwt.go, backend/pkg/utils/password.go, backend/internal/api/router.go</files>
  <action>
Read each file completely. For each file, check against this checklist:

**jwt.go:**
- Empty/weak JWT secret handling (what happens if JWT_SECRET env var is empty?)
- Token signing algorithm pinning (does validation enforce HS256, or could an attacker use "none"?)
- Claims validation completeness (expiry, issuer, audience — what's checked, what's not?)
- Token payload — what claims are included, could any leak sensitive info?

**password.go:**
- bcrypt cost factor — what is it? Is it appropriate?
- Any timing side-channels in password comparison?
- Input length limits (bcrypt has a 72-byte limit — is this documented/enforced?)

**auth.go (middleware):**
- What happens on invalid/missing/expired token? Does it fail closed (deny) or open (allow)?
- Context key injection — are keys typed to prevent collision?
- Does it extract householdID from token? What if user changed households since token was issued?

**cors.go:**
- Allowed origins — are they appropriate for production?
- Are credentials, methods, and headers correctly restricted?
- Does it handle preflight (OPTIONS) correctly?

**router.go:**
- List every route and whether it's wrapped with RequireAuth
- Identify any routes that SHOULD be protected but aren't
- Check for route pattern issues (method restrictions, path conflicts)

Record every finding with: severity (critical/high/medium/low), file:line, description, and why it matters.

**CONCERNS.md already identifies:** empty JWT secret, CORS localhost-only, shopping list missing auth, no rate limiting, no input size limits. Verify these are still accurate and look for ADDITIONAL issues not already caught.

<task type="auto">
  <name>Task 2: Review all HTTP handlers for correctness, input validation, and error handling</name>
  <files>backend/internal/api/handlers/auth.go, backend/internal/api/handlers/household.go, backend/internal/api/handlers/recipes.go, backend/internal/api/handlers/menus.go, backend/internal/api/handlers/shopping.go, backend/internal/api/handlers/offers.go, backend/internal/api/handlers/health.go</files>
  <action>
Read each handler file completely. For each handler method, check:

**Input validation:**
- Is the request body decoded safely? (JSON injection, oversized bodies)
- Are path parameters validated? (empty, wrong format, injection)
- Are query parameters validated? (type coercion, missing required params, injection)
- Is there validation BEFORE business logic runs?

**Error handling:**
- Does `err.Error()` get concatenated into JSON responses? (JSON injection via error messages)
- Are internal errors leaked to clients? (stack traces, SQL errors, file paths)
- Are all error paths covered? (what happens if Decode fails? If service returns unexpected error?)
- Are HTTP status codes correct for each error case?

**Auth context usage:**
- Do protected handlers actually USE the auth context (userID/householdID)?
- Could a user access another user's resources by guessing IDs?
- Are there IDOR (Insecure Direct Object Reference) vulnerabilities?

**Response handling:**
- Is Content-Type set correctly for JSON responses?
- Are responses properly encoded (json.NewEncoder vs string concatenation)?
- Are nil/empty responses handled?

**Method handling:**
- Does each route correctly restrict HTTP methods?
- What happens on wrong method (405 vs fallthrough)?

**Per-handler specifics:**
- `auth.go`: Registration validation completeness, login timing attacks
- `household.go`: Error string matching fragility, invite code handling
- `recipes.go`: Manual path splitting vs PathValue, CRUD completeness
- `menus.go`: Generate input validation, response structure
- `shopping.go`: Missing auth (known), PATCH update safety
- `offers.go`: Coordinate parsing duplication, error message injection (known)
- `health.go`: Information disclosure

Write all findings to `.planning/phases/01-deep-code-review/01-01-FINDINGS.md` combining Task 1 and Task 2 results. Organize by severity (critical first), then by file. Include a summary count at the top.
